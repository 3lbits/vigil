# OWASP ZAP — Local DAST scans with Podman

Quick reference for running OWASP ZAP against a local app in dev.

> **Environment assumptions:** These scans assume local dev with no auth, where the default user
> is `admin`. The spider therefore has full access to the app and covers the whole surface.
> **Never** run against prod.

## Prerequisites

- Podman installed
- The app running locally (adjust the port as needed; examples use `8080`)
- Run the commands from `script/dast/`

**Reports:** All scans write to `script/dast/reports/`. That directory is gitignored, so reports
never end up in the repo. Create it once with `mkdir -p reports` (the make targets below do this
automatically).

**Permissions:** Podman needs write access to save the report. The `:U` flag on the volume mount
chowns the output directory automatically — that's why only `reports/` is mounted, not the whole
`dast/` directory (so tracked files aren't touched). No `chmod 777` needed.

**`host.docker.internal`:** Doesn't always work on Podman. If you get connection refused, use the
host's IP instead:

```bash
ipconfig getifaddr en0           # macOS
hostname -I | awk '{print $1}'   # Linux
```

## 1. Baseline scan (fast, passive) ⚡

Passive analysis only — crawls the app and looks for obvious misconfigs (missing headers, cookies
without flags, etc.). Sends **no** attacks. Takes ~1-2 min.

**Use when:** You want a quick sanity check, or to run in CI.

```bash
mkdir -p reports
podman run -t -v $(pwd)/reports:/zap/wrk/:U \
  docker.io/zaproxy/zap-stable \
  zap-baseline.py -t http://host.docker.internal:8080 \
  -r report-baseline.html -J report-baseline.json
```

---

## 2. Full active scan 🔍

Spider + active attacks (SQL injection, XSS, path traversal, command injection, etc.). Takes
20-60 min depending on app size.

**Use when:** You want an actual security assessment. **Never against production.**

```bash
mkdir -p reports
podman run -t -v $(pwd)/reports:/zap/wrk/:U \
  docker.io/zaproxy/zap-stable \
  zap-full-scan.py -t http://host.docker.internal:8080 \
  -r report-full.html -J report-full.json
```

---

## 3. Full scan with Ajax Spider 🕷️

Like the full scan, but uses a headless Firefox to click through JS-generated links. Much better
coverage on SPA/HTMX apps.

**Use when:** Your app is HTMX-/SPA-based and the standard spider misses routes generated by
JavaScript.

```bash
mkdir -p reports
podman run -t -v $(pwd)/reports:/zap/wrk/:U \
  docker.io/zaproxy/zap-stable \
  zap-full-scan.py -t http://host.docker.internal:8080 \
  -j -m 5 -r report-ajax.html
```

`-j` enables the Ajax Spider, `-m 5` gives the spider 5 min before the active scan starts.

---

## 4. API scan (OpenAPI/Swagger) 📋

If the app exposes an OpenAPI spec, this gives much better endpoint coverage than a spider-based
scan.

**Use when:** You're testing an API endpoint or have a spec file available.

```bash
mkdir -p reports
podman run -t -v $(pwd)/reports:/zap/wrk/:U \
  docker.io/zaproxy/zap-stable \
  zap-api-scan.py -t http://host.docker.internal:8080/openapi.json \
  -f openapi -r report-api.html
```

Other `-f` formats: `openapi`, `soap`, `graphql`.

## 5. The Automation Framework plan (`zap.yaml`)

`zap.yaml` defines a declarative scan plan (passive config → spider → passive wait → summary →
report). It covers roughly the same ground as the baseline wrapper, but it's versioned as code
and easy to extend with more jobs. Use it when you want a reproducible, checked-in scan
definition instead of ad-hoc flags.

```bash
mkdir -p reports
podman run -t \
  -v $(pwd)/reports:/zap/wrk/:U \
  -v $(pwd)/zap.yaml:/zap/plan.yaml:ro \
  docker.io/zaproxy/zap-stable \
  zap.sh -cmd -autorun /zap/plan.yaml
```

The plan is mounted read-only and output (report + `zap_out.json`) is written to `reports/`.

> Note: `failOnError: true` in the plan is meant for CI — it fails the whole run on error. This
> is deliberately different from the wrapper commands above, where `-I` is used locally to drop
> exit codes. Pick the right variant per context: CI = the plan (or wrapper without `-I`), local
> = wrapper with `-I`.

## Useful flags

Work on all wrapper scans (`zap-*.py`):

| Flag | Description |
|------|-------------|
| `-r filename.html` | HTML report (default) |
| `-w filename.md` | Markdown report |
| `-J filename.json` | JSON report (good for CI) |
| `-x filename.xml` | XML report |
| `-d` | Debug output |
| `-I` | Don't return a failure exit code (fine locally) |
| `-m N` | Minutes the spider gets before the active scan (default 1) |
| `-T N` | Max total time in minutes (panic switch) |
| `-j` | Use the Ajax Spider (for SPA/JS-heavy apps) |
| `-a` | Include alpha passive scan rules |

---

## Reading the output

- **PASS** — the rule ran and found nothing
- **WARN-NEW** — new warning since the last scan
- **WARN-INPROG** — warning marked "in progress"
- **FAIL-NEW** — new failure (above the WARN threshold)
- **IGNORE** — rule ignored via config

The exit code is non-zero if there are warnings. Add `-I` or `|| true` locally if you don't care.

## Common problems

**`AccessDeniedException /zap/wrk/report.html`**
Permissions on the output directory. Make sure you're using `:U` on the volume mount and that
`reports/` exists.

**`Connection refused` to `host.docker.internal`**
Use the host's actual IP instead (`ipconfig getifaddr en0` on macOS, `hostname -I` on Linux).

**`403 Forbidden` when pulling from ghcr.io**
Use the Docker Hub image instead: `docker.io/zaproxy/zap-stable`.

**Scan finds few endpoints**
The standard spider doesn't handle JS well. Try the Ajax Spider (`-j`) or an API scan with an
OpenAPI spec.
